# Auto-merge policy

**Rule (CLAUDE.md § Security workflow › Auto-merge policy):** every pull request whose `__HARNESS_CI_WORKFLOW__` run is green is squash-merged, pinned to the commit CI validated, and its head branch is deleted; documentation-only pull requests included, since the CI workflow runs on every pull request: nothing merges without a green CI run. Nothing that touches Claude instruction files, nothing from a CI Claude session's branch, no Dependabot bump the gate holds and, once `TEST_HOLD_RE` names the project's tests, nothing that deletes or rewrites lines of an existing test is ever merged unattended.

## Status

The workflow this module was ported from runs in production. The two sign-offs (CI and the automated review) are new to this variant: their logic is run by the guard on tables of runs, never against GitHub. This generic variant — the same two jobs, without the post-merge deploy dispatch and with the project-specific values turned into settings — has run on the kit's own repository (`promote-docs`, twice, holding a pull request that touched gated paths) and **once, on 2026-11-12, in a throwaway private repository (the kit at commit `e677e3d` plus the `actions: read` fix of `claude-rework`; `claude-code-action` at `f27be6b`, which installed Claude Code 2.1.302)**, with the automated review installed. There it merged a docs-only pull request at once, without CI; merged code pull requests only after both CI and the review were green, the run started by CI's end leaving the merge to the one started by the review's; merged a pull request retargeted onto the default branch after the run its `edited` event started; held a change to `CLAUDE.md` and a Dependabot bump of the Claude action; and did nothing after a held review, re-run or not. A second live run followed on 2026-11-13, in a throwaway private repository again, with `TEST_HOLD_RE` set through the installer: a pull request that only added a test merged on green, and one that reworded a line of an existing test passed the review and was held by the gate, its draft lifted; one that removed an assertion was held earlier, by the review. Not exercised: a deleted test line held by the gate, a re-run review that passes, a workflow-touching merge refused for want of `workflows`. That repository's default branch was reported unprotected by GitHub's branch API, so the ruleset prerequisite was not exercised either. Since those runs, the range is listed from the base branch's tip instead of `base.sha`, and a listing of 300 files holds whatever the count (§ The gate judges what is merged); the hold at 300 has run only against a local stand-in for the API, the listing from the tip ran in the third live run below. A third live run, on 2026-11-14, in a throwaway private repository, built heads that had merged two branches before both landed with merge commits, so that the head and the tip had two merge bases. GitHub's compare and its diff of the pull request started from the more recently committed of the two; where a docs-only pull request was merged that way, its test merge and its squash merge did too, and the held page the head had set back through the other merge base was neither listed nor changed. With the other date order, GitHub's diff of the pull request listed the held page. The same run found a pull request's test merge (`merge_commit_sha`) still built against an old tip forty minutes after the base branch moved, `mergeable` reading `true`. In that run both jobs read the tip and listed the range from it on GitHub, before a listing of the test merge, tried then and removed since, held the code pull requests. The reads before each merge call and the check of what the merge wrote (AM-10), added after that run, have run only against the stand-in. Watch the "Auto-merge after CI" runs on a docs-only pull request and on a code one before relying on it. Since then the documentation fast path (`promote-docs`, a `pull_request` job that merged a documentation-only pull request at once, without CI) is gone, and every merge waits for CI (AM-11): that change is unit-tested only — the guard on tables of broken copies, the CI skeleton's `changes` script on a table of changes — and has not run live.

## Why

When one maintainer (or a few) works through several sessions in parallel, a green pull request waiting for a click is delay without control: nobody reads the diff at that moment, the CI already did the reviewing. So there is no heuristic here — green means merged — and what does need a human is named and held: the files every later session will execute, the branches a CI agent wrote, the dependency bumps that can break.

The price is that the CI workflow *is* the review, unless the project adds the automated review (`.github/workflows/claude-review.yml`), which must then sign off too (§ The gate judges what is merged). Whatever must hold before a change lands (tests, the security gate) has to be part of one of them, and the limits below have to be acceptable to you.

## How it works

`.github/workflows/auto-merge.yml` has one job, on one trigger (AM-11):

- **`promote-from-ci`** — `workflow_run` on `__HARNESS_CI_WORKFLOW__` and on the automated review, for every pull request, documentation-only ones included. It acts on a successful CI run that a `pull_request` event started from a branch of this repository (never a fork), or on a successful review run that `workflow_run` started from `.github/workflows/claude-review.yml`, and merges only once both have signed off (§ The gate judges what is merged).

The merge is a synchronous server-side call (`PUT /repos/…/pulls/N/merge`, squash first): no checkout, no local git, nothing from the pull request is executed. A merge commit is made only when GitHub refuses squash as a method (`Squash merges are not allowed`: the repository's settings); any other failed call is tried again, squash again, after a wait and the reads below (§ The gate judges what is merged). A call that answered a 5xx or nothing may have merged: a head pushed after it ends the run red, where it would otherwise leave the pull request to its new head's run (§ The merge is the commit CI validated). A merge commit puts the head's commits on the base branch, which moves the merge base of any pull request built on that head and stops its run. Native auto-merge (`gh pr merge --auto`) is not used because it depends on a repository setting GitHub does not offer on every plan for private repositories; since `workflow_run` only fires once CI has concluded, a synchronous merge leaves no window worth closing. Right after it, a step lists what the merge commit changed and runs the gate's rules on it again: the run turns red, after the fact, when the merge wrote anything the gate holds (§ The gate judges what is merged).

**A documentation-only pull request waits for CI too.** The CI workflow runs on every pull request, with no path filter, and skips its costly jobs when only documentation changed (§ Setting it up). Its first job, the enforcing tier of `security.yml`, always runs: a secret pasted into a Markdown file is scanned before it can land. The price is one short run per documentation pull request. Holding one works as for any other: cancel its CI run.

## What is never merged unattended

### Claude instruction files (AM-1)

`CLAUDE.md`, `.claude/agents/*.md`, `.claude/skills/**`, `.claude/settings.json`, a git hook: these are executed, not read. Every session that opens the repository loads them, an agent definition decides which tools a sub-agent may run, a settings hook runs a shell command on every matching tool call. Most of them are Markdown, so a CI that skips documentation would wave them through — and a green CI proves nothing about them anyway. A session steered by content it read could widen an agent's tools or delete a rule, and every later session would load the result.

So the workflow never merges a pull request that touches a path matched by `CLAUDE_GATE_RE` or `PROJECT_GATE_RE` (two patterns in the workflow's `env`, applied together). `CLAUDE_GATE_RE` is the kit's list: any `.claude/` directory at any depth and a bare `.claude` entry (a symlink); `CLAUDE.md`, `CLAUDE.local.md` and `AGENTS.md` anywhere (Claude Code reads an `AGENTS.md` as instructions where no `CLAUDE.md` stands in for it, a subdirectory's included); `.githooks/`; `.mcp.json`; the other files a Claude CI action reads as configuration from its working directory (`.claude.json`, `.ripgreprc`, `.gitmodules`, `.husky/`); what runs Claude in CI and this workflow — `.github/workflows/claude*.yml`, `auto-merge.yml` itself; and the gate with everything it runs or reads. That last group is `scripts/security-checks.sh` and `scripts/guards.d/**`, which git runs on each push through the pre-push hook, which the read-only agents run, and which enforce all of this; every script the kit ships for its guards and workflows to run, with its test and what it reads (`scripts/plugin-pins.mjs`; `scripts/fetch-pinned-release.sh`, which the security workflow runs; `scripts/weekly-digest.mjs` and its settings, which the scheduled digest runs with a token that writes issues; `scripts/audit-gate.mjs` and `scripts/audit-allowlist.json`, its list of accepted advisories, and any `.npmrc`, which decides what npm audits and where it asks; `scripts/parallel-sessions.sh`, which the gate runs on a contributor's machine; `scripts/eco-design-audit.mjs` and `scripts/eco-design.config.json`, which name the code the eco-design workflow fetches and runs on every pull request — a test of the kit keeps every file a module ships to be run or read in the list, or names why not); the scanner configs that decide what is reported (`.gitleaks.toml`, the `.gitleaks.json` gitleaks would read before it — the kit's own calls name `.gitleaks.toml` — `.gitleaksignore`, `.github/zizmor.yml` and a `zizmor.yml` at the root — an ignore added there silences a finding for everyone); `scripts/reviewed-plugins.json`, the record of which Claude Code plugin commits were reviewed; `scripts/auto-merge-paths.txt`, the table below; the findings catalogue at the root (`SECURITY_REVIEW*.md`), which the automated review reads as its standards; and the convention pages (`docs/conventions/`), which `CLAUDE.md` sends every session and the review to — Markdown, so a CI that skips documentation would wave a change to them through. A pull request that adds or edits a convention page is therefore merged by hand. A pull request that adds a regression guard is therefore merged by hand too. The match is case-insensitive per path segment, because a case-insensitive file system turns `.Claude/agents/x.md` into `.claude/agents/x.md`.

#### Paths of your own

What else your tooling executes — another agent's instruction file, a page of install commands that sessions follow, another hooks directory, a script one of your own guards runs — goes in `PROJECT_GATE_RE`, never in `CLAUDE_GATE_RE`: the kit's list then stays what the kit ships. It is the same kind of pattern, matched the same way; as shipped it is `^$`, which matches no path. It is set through the installer (§ Setting it up), not by editing the workflow. An empty or unusable pattern holds every pull request.

Each addition comes with rows in `scripts/auto-merge-paths.txt`, which is yours: `hold <path>` for a path the gate must hold, `pass <path>` for a neighbour that must keep merging on green. AM-1 runs the two patterns together on every row, so a pattern that misses its target, or catches too much, fails the gate — there is no need to copy the check into `50-project.sh`.

The pattern lives in the workflow file because the workflow checks nothing out: it has no file of the repository to read. Editing that one line makes `auto-merge.yml` a kit file edited in the project — the kit's `update` will report it rather than refresh it, and HD-1 lists it. That is the cost of a gate that executes nothing from the repository.

What is not in the kit's list, and is yours to decide: a script one of your own guards runs or reads, and the workflows that call the gate (§ Residual risks).

Such a pull request stays open until someone merges it from the GitHub UI. A mixed one (code plus a `CLAUDE.md` bullet) waits too; keep the instruction change in the same pull request anyway, the hand merge is the price of the rule.

### Tests that get weaker (AM-8)

Green means merged, and green is whatever the tests say. The CI run that just passed ran the tests *as the pull request left them*: a session that could not make a test pass and rewrote its assertion, or deleted the test, gets the same green as one that fixed the code — and here nobody reads the diff at that moment.

`TEST_HOLD_RE`, a third pattern in the workflow's `env`, names the tests (and their fixtures and snapshots). The gate reads, from the immutable range, what each changed file is: a pull request is held when a file matching the pattern is **deleted**, **renamed** (old or new path), has **a line removed or rewritten**, or changed with no line count at all (a binary snapshot, a file mode). What keeps merging on green: a **new** test file, and **lines added** to an existing one — writing tests is never slowed down, taking something away from them is. A held pull request is marked ready by `promote-from-ci` like any other.

As shipped the pattern is `^$`, which matches no path, so nothing is held until the project says where its tests are — the kit does not guess a layout. A typical value is `'(^|/)tests?/|\.(test|spec)\.[a-z]+$'`. Each kind of path comes with a `test <path>` row in `scripts/auto-merge-paths.txt`, and a `not-test <path>` row for a neighbour the pattern must not catch; AM-8 runs the pattern on them. An unusable pattern holds every pull request that changes an existing file.

This is a tripwire, not a proof that the tests still test. It does not see a test neutered by **added** lines only (an early return, a skip marker — forbid those with a lint rule that CI runs), a test runner's configuration that stops collecting a directory (put that file in the pattern), or code changed so that the assertion no longer exercises it. And a refactoring that legitimately rewrites tests is held with the rest: that hand merge is the price, as for instruction files.

### Branches written by a CI Claude session

The job refuses a `claude/issue-*` head in its `if:`. A Claude session running in CI wrote that branch, and opening its pull request is not reading it. Branches named `claude/<anything else>` by local sessions keep the normal path.

### Dependabot bumps the gate holds (AM-5)

A Dependabot pull request is not written by a maintainer, so the gate in `promote-from-ci` looks closer:

- **Every commit must be Dependabot's.** A commit pushed onto its branch would otherwise ride the exception unreviewed.
- **Patch and minor bumps merge.** Reading a minor's diff by hand was never the control. The CI is, and so is the `cooldown` in `.github/dependabot.yml`, which keeps a version published minutes ago out of version updates. The guard notes an update entry that has none.
- **Held:** a major (as the trailer says it, or as the version pair shows it — below 1.0 a minor is breaking, below 0.1 a patch is); a move to a pre-release; a version that is not a whole version token (a SHA, a digest); a **GitHub Action minor**, since an Action runs with the workflow's token and secrets; and any pull request whose trailer entries and `from X to Y` lines do not name the same set of dependencies, so a bump written in another shape cannot go unchecked.
- **One exception, off as shipped.** An entry typed `dependency-type: indirect` is a security update — version updates cover direct dependencies only, which is why AM-5 fails on the word `allow` in `dependabot.yml` — and its major can be the only fix. Such a major goes through unless the pull request touches a path matching `MAJOR_HOLD_RE` (`.github/` is always held). The shipped value `.` matches every path: every major waits for a hand merge. Narrow it to the directories whose dependencies the pull-request CI does not build or test (`'^(mobile|infra)/'`), or to `'^$'` when CI exercises everything. A direct dependency's major always holds; an empty or unusable pattern holds everything.

The verdict is read from Dependabot's commit message (the `updated-dependencies` trailer and the bump lines). The usual metadata action resolves the pull request from the event context, and `workflow_run` carries no pull-request payload, so it cannot be used here. Anything but an exact `merge` verdict holds.

## A held pull request is handed over (AM-4)

Once the gate has decided, `promote-from-ci` marks the pull request ready — whichever way it decided, and only while its head is still the commit CI validated. For a held pull request that is all that happens: the merge button works at once. **Ready is sticky**: nothing turns a pull request back into a draft, so a handed-over one stays ready after a later push, even while that push's CI is pending or red — read the head's checks before a hand merge.

## The merge is the commit CI validated (AM-6)

`find-pr` keeps only the open pull request whose head *is* the SHA of the green run (a `sha:` search also returns stacked and sibling pull requests), and every merge call passes that SHA. A commit pushed after CI finished gets a 409 — or is seen by the read before the call, or by the one after the last call, which end the job the same way —: no retry, no merge, the job ends green with a notice, and the new head's own run merges it. After a call that answered a 5xx or nothing, which can merge, the job ends red instead, and says to check whether the pull request is merged (§ The gate judges what is merged). The SHA always comes from the triggering event, never from the pull request's current state — reading the current head would merge exactly the commit nobody tested.

## The gate judges what is merged (AM-7)

Pinning the merge is half of it. The gate must read the same commit. A listing of the pull request's *current* files describes whatever its head and base are at the instant of the call: someone with push rights — a steered session is enough — could move the head or retarget the base, let the gate list an innocent diff, and put things back before the merge call, which only checks that the head equals the validated SHA.

So the gate never lists the pull request live. One read gives its base branch, its head, its file count and its author; if the head is no longer the event's, the job stops. Files and commits then come from the immutable range `compare/<base branch's tip>...<validated head>`, which no later push can change. A listing of 300 files, the most the compare returns, holds whatever the count: the pull request's own count can come from another merge base than the tip's — GitHub documents that its compare pages and pull request pages may show different changed files for the same branches, each from its own merge base, and the gate assumes the API's `changed_files` and the compare can differ the same way — so equal counts would not prove a whole listing. Any gap between the two counts holds too, and so does a commit list cut short (250 commits, read for a Dependabot pull request).

**The range starts at the tip, not at the pull request's `base.sha`.** GitHub sets a pull request's base to the commit its base branch references and does not move it when the branch moves, while a squash applies the head's changes since its merge base with the base branch *as it is when the merge is made*. The two differ when a branch the head had merged lands on the base branch afterwards: a held path that branch changed, and that the head set back, is then changed back by the merge, and a range from `base.sha` does not list it. So each job reads the tip itself, by its full ref (`git/ref/heads/<branch>`, which no tag of the same name can answer), right before listing; a tip that cannot be read fails the job. Reproduced with the workflow's own steps against a local stand-in for the API, which is not in the repository: from `base.sha`, a squash that set `.claude/settings.json` back, one that restored a removed hook and one that set a convention page back all merged; from the tip all three were held.

**Before each merge call, retries included, the merge step reads again what the gate read.** The pull request first. Merged already by this workflow's token (`github-actions[bot]`, as GitHub reports a merge made with `GITHUB_TOKEN`), it is a merge an earlier call made and answered with an error: its merge commit goes to the check below and the step ends. Merged by anyone else, it is a person's merge: the step ends and nothing is checked or deleted. Closed without a merge, retargeted, or with a head pushed since the validated commit, the step stops: a closed pull request is left as it is, a moved head to its own run, as a 409 would leave it. A moved head ends the run green only while no call before it answered a 5xx or nothing. A call refused with an HTTP 4xx merged nothing; one that answered a 5xx, or did not answer, can have merged, the pull request showing it late and taking the push meanwhile: the run is then red, and its message says to check whether the pull request is merged and to read the merge commit if `github-actions[bot]` made it. A 409 after such a call is red the same way. Each field of that read is a word, `-` for one GitHub does not send, so that a missing field cannot shift the next ones: a merge commit GitHub does not name reaches the check as `-`, which it refuses — an answer without `merge_commit_sha` (a newer version of the REST API drops it from pull requests) fails red, never silently. Then the tip: the tip moves with every merge, but what this merge writes is the head's changes since its merge base with the tip, which moves when a commit of the head lands. So when the tip moved, the step reads the merge base the head now has with it and stops if it is not the one the gate listed from; a pull request whose base branch merely moved on merges. A merge base that is the head itself means the head is on the base branch already — a merge commit an earlier call made, which the pull request does not show yet —: no other call is made, and the next read hands it over. After the last call the pull request is read once more, for the same reason: merged by this workflow's token, its merge commit goes to the check; merged by anyone else, closed, or with a head pushed since, the step ends as it would before a call; otherwise the run is red, and its message says that the pull request is not shown merged by this workflow — a call can merge and answer an error, and the pull request can show it late —, to check whether it is merged, to read its merge commit if `github-actions[bot]` made it (a re-run does not check it), and to merge it by hand if it is not merged. A stop leaves the pull request ready and unmerged; a re-run of the workflow judges it again. A failed read fails the job, and its message says to check whether the pull request is merged, since a call before it may have merged it.

**What the merge wrote is judged again (AM-10).** The compare lists the head's changes since one merge base of the head and the tip. When they have two — the head merged two branches that both landed later with merge commits — git's own merge starts from both, and a held path that one of them changed and the head set back would be changed back by the merge without being listed. GitHub's merge was seen to start from the one its compare names (§ Status), so the listing is what it writes; nothing documents that. So right after the merge, a step reads the commit GitHub created, lists it against its first parent — the tip it landed on, whichever that was at the instant of the call — and runs the gate's rules on that listing: `CLAUDE_GATE_RE` and `PROJECT_GATE_RE`, and the selection of weakened tests under `TEST_HOLD_RE`. A match, a listing of 300 files or a listing that cannot be read turns the run red. It comes after the fact: the merge is done, so it reports instead of holding, and the commit it names is the one to read and revert. A dispatch added after the merge (§ After the merge) goes after this step and does not run when it is red.

**GitHub's test merge is not read.** A pull request's `merge_commit_sha`, the merge GitHub builds to test mergeability, was seen still built against an old tip forty minutes after the base branch moved, `mergeable` reading `true` all along. Read as a second listing, it held every pull request whose base branch had moved since its last push; and it is built by the same merge engine that AM-10 checks after the fact.

A read that fails is not a head that moved. If the pull request cannot be read from the API, the job fails with an error and merges nothing; it does not end green on a "head moved" notice that nobody would look at. No call is fed straight into `read` through a here-string, where a failure leaves the variables empty and the step successful.

`workflow_run` fires once per workflow it lists, and on whichever finishes. The list holds two names: the CI workflow and `Claude review`, the automated review, which CI's end starts. Neither name is trusted. A review run is accepted only when it was itself started by `workflow_run` from `.github/workflows/claude-review.yml` — a file that only the default branch's copy can run that way — and the commit it reviewed is read from its run name (`Claude review of <sha>`), which only that file sets; the pull request's own head branch is then checked against `claude/issue-*`. A sign-off step lets the gate run only when **every** CI run of the commit is green (by name; a flaky run may be re-run, but a green run cannot cover a red one, so a copy of the CI workflow run from another pull request cannot hide a failure) and, when `.github/workflows/claude-review.yml` exists on the default branch, **every** review run naming the commit is green at its first attempt — among the review's latest 100 runs. A hold therefore stays a hold for that commit while it is among those 100 runs, and a review re-run until the model says pass holds too; a new commit, or a hold pushed out of the window by many CI runs, gets a fresh review (`claude-review.md` § The verdict). Without that file the review is not required and its name never fires. The pull request is the only open one into the default branch with that head, and the gate holds it if its base is no longer the default branch: a pull request retargeted elsewhere, or a second one on the same commit into another branch, is never merged by this job. A review still running means its own end will start the workflow again; a review that held leaves the pull request to a human (its comment says why). Dependabot's pull requests are not reviewed and keep their own gate. Any other check that must hold before a merge belongs in the CI workflow, called as a reusable workflow so that one conclusion covers both.

The job has a `concurrency` group keyed on the commit judged (written as the review names it), so that CI's end and the review's end do not both try to merge. Pull requests never share a group; for one commit, a run left pending and replaced by a newer one loses nothing, since the newer one re-reads everything (§ After the merge explains why no group spans pull requests).

## A pull request runs its own copy of this workflow

`promote-from-ci` is started by `workflow_run`, which runs the workflow as it stands on the **default branch**: a pull request that edits `auto-merge.yml` does not change what judges it. That is why `workflow_run` is the only trigger (AM-11). A `pull_request` trigger runs the workflow file **as the pull request writes it** — observed on the pull request that installed this workflow in the kit's own repository, when it still had a documentation job on that trigger: the job ran from the branch before the file existed on the default branch. A job on it would hold a write token while running a copy the pull request chose.

The CI workflow is different: it runs on `pull_request`, so a pull request that rewrites it is judged by its own version, and `promote-from-ci` then sees a green run. Nothing inside this workflow can close that: the file that would check is the file being changed. What closes it sits outside the pull request, in the repository's settings (§ Setting it up, the ruleset). Without that ruleset, the claim of this page is narrower than it reads: instruction files are held against a pull request that leaves the workflows alone, not against one that rewrites them. GitHub usually refuses to merge a workflow change with the job token, which stops such a change from landing unattended.

## After the merge

**A merge made with `GITHUB_TOKEN` emits no `push` event** — GitHub's guard against workflows triggering workflows. Anything you run on a push to `__HARNESS_DEFAULT_BRANCH__` (a deploy, a post-merge test run) does not run after an auto-merge, and nothing reports that it did not. The symptom is a merged pull request that never shipped.

The workflow dispatches nothing by default, which leaves one honest limit: `__HARNESS_DEFAULT_BRANCH__` is not re-tested after an unattended merge. A pull request's CI validated its head merged with the default branch as it was when the run was created; if another pull request landed meanwhile, nothing has tested the two together until the next run on the default branch.

`workflow_dispatch` is the documented exception: it does create a run when invoked with `GITHUB_TOKEN`. To have a run follow each merge:

1. Give the target workflow an `on: workflow_dispatch` trigger (with a `merged_sha` input if it should know which merge started it).
2. In `promote-from-ci`, add `actions: write` to the job's permissions and, after the check of what the merge wrote and before the branch cleanup, a step conditioned on `${{ !cancelled() && steps.merge.outputs.merged == 'true' && steps.check.outcome == 'success' }}` that runs `gh workflow run <file> --ref __HARNESS_DEFAULT_BRANCH__ -f merged_sha="$MERGE_SHA"`, with `MERGE_SHA: ${{ steps.merge.outputs.sha }}` passed through `env:`. A red check means the merge wrote something the gate holds: nothing should deploy or vouch for it. The cleanup stays last: a failed deletion must never cost the dispatch.
3. No loop: the dispatched run's event is `workflow_dispatch`, which `promote-from-ci` ignores.
4. If the dispatched run skips tests because "the pull request was green", it must not skip them when the default branch moved during the pull request's CI. Decide that **after** the merge (commits on the default branch since the CI run was created, minus the merge commit itself — decided before, two merges seconds apart both see "nothing moved"), fall back to the full run on any doubt, and have the target workflow honour the shortcut only while the default branch's head still is `merged_sha`. If it deploys, the deploy waits for every test job. These are the invariants AM-2 and AM-3 pinned in the workflow this one comes from; bring them back in `scripts/guards.d/40-auto-merge.sh` with the dispatch.

No `concurrency` group spanning pull requests belongs on these jobs: GitHub keeps one running and one pending run per group and cancels the older pending one, so with three merges in a minute one pull request would silently not be merged. Runs for different pull requests are safe concurrently — the merge call is atomic per pull request. The only group is per commit (§ AM-7 above).

## Head branch deletion

GitHub's "Automatically delete head branches" setting was observed not to apply to merges made with `GITHUB_TOKEN`, so the job deletes the head ref itself, under the `contents: write` it already holds:

- **Only after an actual merge.** The merge step sets `merged=true` only when the call succeeded; a deferred, held or failed pull request keeps its branch.
- **Guards:** a branch of this repository only; never the default branch; never a branch another open pull request is stacked on or opened from (GitHub would retarget or close it); only a name made of `[A-Za-z0-9._/@+-]`, since it becomes a URL path segment — anything else is left to a human with a warning.
- **Look before deleting:** an exact ref lookup first. A ref already gone is the goal reached (Dependabot deletes its own); a tip that differs from the merged head means someone pushed since the merge, and the branch is kept; a lookup or a deletion that fails fails the step and names the branch.

A session still working on a merged branch is unaffected: a push before the cleanup keeps the branch, a push after it recreates it, as after a hand merge.

## Four things that surprise

- **Draft does not pause a pull request.** `promote-from-ci` lifts the draft and merges, documentation-only pull requests included. To hold a pull request, cancel its CI run (`gh run cancel <id>`) or close it — closed while a run is about to merge it, it is left closed and the run ends green —; the draft badge only changes the GitHub UI.
- **A pull request touching `.github/workflows/**` may be refused at merge while CI is green.** GitHub can refuse to let `GITHUB_TOKEN` land a change to a workflow file without the `workflows` permission; the merge then fails five times and the auto-merge job goes red although the CI workflow is green — the failure is here, not in a test. Both outcomes have been observed with the same permissions, so check the job on such a pull request rather than assume. If it is refused, merge by hand. **Never grant `workflows: write`**: any green pull request could then rewrite the pipeline unattended.
- **Dependabot pull requests merge too**, unless the gate holds them (above). A held one stays open and is marked ready; the run's notice says why.
- **A merged pull request can leave a red run.** The check after the merge (AM-10) reports, it cannot undo: a red `Check what the merge wrote` names a commit already on the default branch. Read it and revert what nobody reviewed. Do not re-run it to make it green: the re-run ends green without checking anything.

## Setting it up

- **The CI workflow.** A workflow named `__HARNESS_CI_WORKFLOW__` must exist and run on `pull_request`, with `edited` among its types (AM-9: a retargeted pull request must get a run of its own); until it exists, nothing is merged (the guard notes it).
- **It runs on every pull request, with no `paths` or `paths-ignore` filter.** A pull request it skips gets no run: this workflow never merges it, and where a ruleset requires the CI checks, nobody can merge it without a bypass — a required check that never reports is not a pass. To spare the build on documentation, the CI workflow skips its costly jobs instead: a cheap `changes` job says whether anything outside the documentation set changed, and each costly job declares `needs: [changes]` and `if: needs.changes.outputs.code != 'false'` (an empty verdict runs the job). GitHub counts a job skipped by its `if:` as a passing required check. The job that calls `security.yml` never waits for it. The `ci-workflow` module ships that shape and its guard (CW-1 to CW-3, `docs/conventions/ci-workflow.md` where it is installed).
- **A ruleset on the default branch, before the first pull request.** The gate cannot protect itself from a pull request that rewrites it (§ A pull request runs its own copy of this workflow). In the repository's settings, protect the default branch with a ruleset (or a branch protection rule) that: refuses direct pushes, so every change is a pull request; requires a review from a code owner for `.github/workflows/**`, through a `CODEOWNERS` entry, so a pull request that touches a workflow cannot be merged by a job token alone; and gives GitHub Actions no bypass. Leave the required approvals for other paths at zero, or nothing merges unattended. **Check that it is enforced, not only saved.** On a private repository GitHub accepts a ruleset on some plans without enforcing it — the Rulesets page then says so in a warning, as seen on the kit's own repository while it was private under a personal account. Where it is not enforced, do not install this module: nothing stands between a pull request that rewrites the workflow and the default branch. Where it is, open a pull request that edits a workflow and watch the merge refused. The kit's authors have not tested the ruleset itself.
- **Three settings are values of the installation, not edits of the workflow:** the paths of your own that are executed (`PROJECT_GATE_RE`, with their rows in `scripts/auto-merge-paths.txt`), the paths of your tests (`TEST_HOLD_RE`, with `test` rows in the same file) and where a Dependabot major is held (`MAJOR_HOLD_RE`). The kit's installer writes them into the workflow's `env` and records them in `.claude/harness.json`: `node <kit>/bin/harness.mjs update . --set TEST_HOLD_RE='(^|/)tests?/'`. Set that way, the workflow stays a kit file the project has not edited, and an update of the kit refreshes it with the project's values in place; edited by hand, it is a conflict at every new version. A value holds no single quote and no line break; AM-1, AM-5 and AM-8 check that each is a usable pattern.
- **One decision is an edit of the workflow:** whether something must be dispatched after a merge (§ After the merge). From then on the file is one the project edited: `update --merge` carries the edit over a new version of the kit when the two do not overlap.
- **Forks are out of scope by design**: the job acts on branches of this repository only.

## Residual risks, accepted

- Documentation other than the gated files merges on a green CI run whose costly jobs were skipped: the secret scan and the gate judged it, nobody reviewed it before it lands. The convention pages under `docs/conventions/` are gated, since `CLAUDE.md` sends every session and the automated review to them; a page elsewhere that `CLAUDE.md` points to is not — put it in `PROJECT_GATE_RE`.
- The CI workflow runs as the pull request writes it, its `changes` job included. A pull request that rewrites it is judged by its own copy; only a ruleset on the default branch stands in the way (§ A pull request runs its own copy of this workflow).
- The gate holds the gate runner and the guards, but not the workflows that call them (`security.yml`, the CI workflow): GitHub usually refuses to merge a workflow change with the job token, which is not a guarantee. The checks stop a regression, not a deliberate edit by someone who can change what runs them.
- The API pins the head of a merge, not its base. The pull request, the tip and, when the tip moved, the merge base are read again right before each merge call; a pull request retargeted in the instant between those reads and the call would be merged into its new base, against which the gate did not judge it, and a branch the pull request contains, landed in that instant, would move the merge base again. The check of what the merge wrote sees the second after the fact, and the first only through the gate's rules on what landed (AM-10).
- **A head and a tip with two merge bases.** The listing is what GitHub's merge writes only while GitHub's merge starts from the merge base its compare names — seen live (§ Status), not documented. If it ever started from both, as git's own merge does, a held path set back through the other one would be merged unattended, and only the check of what the merge wrote would show it: a red run, after the fact.
- **A rename on the base branch.** The gate lists the paths the head changed. When the base branch has renamed one of them since the merge base — into a held path, say, through a pull request a person read as a move — git's merge follows the rename and writes the head's change there. The listing does not show it, and the merge base does not move when such a rename lands between the gate and the merge call: only the check of what the merge wrote shows it, red after the fact. Closing it before the merge would mean listing what the base branch renamed since the merge base; that is not done here.
- A pull request merged by hand, or closed, while the run is between its gate and its last read is left alone: nothing checks or deletes what a person merged. Both are read from what GitHub says: an answer that names no merger reads as a hand merge, and a pull request read as closed and not merged is taken for one a person closed, even after a call that answered a 5xx — were GitHub ever to show a merge of this run either way, that merge would go unchecked. A head pushed since is not taken on trust that way: after such a call the run is red.
- **A head pushed after a call that answered a 5xx or nothing turns the run red**, whether or not that call merged: the run cannot tell, so its message says to check. A call refused with an HTTP 4xx answer is taken to have merged nothing, which was not tested live; a refusal that merged would leave a head pushed since green and the merge unchecked.
- **A red check is the report, once.** After a merge the pull request is closed, so a re-run of the job finds no open pull request and ends green without checking again. Read the commit the red run names instead.
- A pull request stopped before its merge call — a commit of its head landed meanwhile, or it was retargeted — is left ready and unmerged, with a notice; nothing runs the workflow again by itself. One whose head was pushed since is left to the run of its new head, before a call or after the last one.
- A merge commit is made only on GitHub's answer `Squash merges are not allowed`, the text the local stand-in gives; it was not checked live. Worded otherwise — where a ruleset limits the merge methods, say — the run fails red after its five attempts and leaves the pull request for a hand merge.
- The automated review reads its diff from the tip when it starts; the gate reads the tip again once the review's end starts it, up to the review's timeout later. A branch the head contains, landed in between, moves the merge base: the gate then lists changes the review did not read, and merges them unless a held path is among them.
- A pull request whose range from the tip lists 300 files, or more than 250 commits for a Dependabot one, cannot be listed completely from the immutable range: it is held for a hand merge.
- A Dependabot entry's `indirect` type is trusted from the commit text; it is not cross-checked against an open alert.
- Security updates are not subject to `cooldown` (GitHub documents it as a version-updates option): a fix version merges as soon as its CI is green.
- Without a post-merge dispatch, the default branch is tested before the merge only (§ After the merge).
- **A CI run is known by its commit and its workflow name, not by the pull request that started it.** For a `pull_request` event GitHub takes the workflow file from the pull request's merge commit, so someone who can push can open a pull request into a branch of their own whose copy of the CI workflow simply succeeds. Since every CI run of the commit must be green, such a copy cannot hide a red run of the real one. What it can do is stand in for a run that never happened: a pull request opened into that branch and retargeted to the default branch while the copy runs gets no run of the real workflow unless the CI workflow reacts to `edited` (AM-9 requires it; the kit's `ci.yml` does), and a pull request with a merge conflict gets no run at all (its merge is refused too). The review is out of reach of this: its runs are started by `workflow_run`, from the default branch's file only. **The boundary is a check GitHub requires, not one this workflow reads**: where your plan offers it, a ruleset on the default branch that requires a workflow to pass, run from the default branch, makes a forged copy useless. It has not been tested by the kit's authors.
- `TEST_HOLD_RE` holds nothing as shipped, and once filled it sees removed and rewritten lines only: a test disabled by added lines, or by a change outside the pattern, still merges on green (§ Tests that get weaker).

- **AM-9** — the CI workflow waited for lists `edited` among its `pull_request` types, so a pull request retargeted to the default branch gets a run of its own. A heuristic on the `types:` line: a workflow that says it another way fails until it says it plainly.
- **AM-7** — the gate judges the range that is merged: no listing of the pull request's current files or commits; three compare calls per merging job — the gate's on a pinned line that lists `compare/${TIP}...${HEAD_SHA}`, the merge base read again before a merge call, and AM-10's —; each gate holds a range that comes back without its merge base; the tip read by its full ref after a check of the branch's name, both pinned, and named on four lines of each job's gate and merge steps only — its read, its check, the listing and its hand-over to the merge loop, all pinned — so that no other line of those steps takes it again (a message or a comment on a code line counts too; the workflow-level env, where the project's patterns live, does not); the tip and the merge base the gate judged handed to the merge step on one pinned line each, and every line of the gate and merge steps naming them, the values read before each call, or `CALLED`, counted (each step runs in a shell of its own: another step, a dispatch after the merge say, may use the same names, and retry in the merge loop's own words — the pins of the loop read the merge steps only); before each merge call, retries included, the pull request, the tip and, when the tip moved, the merge base read again — from the head of the attempts' loop to the call, comments and plain messages aside, nothing but those reads: a merge this workflow's token made handed to the check, a merge by anyone else left alone, a closed pull request, a retarget, a head pushed since or a moved merge base stopping the merge — a head pushed since red once a call answered a 5xx or nothing (`CALLED`) —, a head already on the base branch making no other call, a failed read failing the job, every field of the read a word (`-` for one GitHub does not send); after the last call, the pull request read once more, a merge this workflow's token made handed to the check, a merge by anyone else, a closed pull request or a head pushed since ending as before a call, nothing else up to the step's end; the rows and their count on pinned lines, assigned nowhere else; no `base.sha`, `base_sha` or `BASE_SHA` in the jobs and no compare from `${BASE…}` or `${DEFAULT…}`; a listing of 300 files, or a gap with the pull request's count, held by a branch that only reports and exits; a head check before the file count is trusted; and the base branch taken from the gate. A pull request or a tip that cannot be read fails the job. These are checks on the text: they catch a regression, not every way of rewriting the workflow, which is itself held.
- **AM-8** — the workflow's own selection of weakened files is extracted and run on the file shapes a compare listing returns (new file and added lines pass; a deletion, a rename, a removed or rewritten line, a change without line counts are listed); `TEST_HOLD_RE` is defined once, its definitions counted as AM-1 counts its two, and usable, every merging job applies it to that selection and only reports and exits on a match; the `test` / `not-test` rows of `scripts/auto-merge-paths.txt` get their stated outcome. Needs `jq`: without it the selection is not run locally, and the check fails on a runner.
- **AM-10** — right after the merge step of each merging job, as the next step of the job, named or not, a step `Check what the merge wrote` runs whenever its merge happened (`!cancelled()`), reads the merge commit the merge step hands it, with nothing else before its run block. Its run block, comments and plain messages aside, is pinned: the commit's first parent read, `compare/${PARENT}...${MERGED}` listed and its shape checked — each read up to three times, five and ten seconds apart, since a commit just written can take a moment to be readable —, the gate's patterns and its selection of weakened files run on it (the selection compared as a string with the gate's), and every way out but the last an `exit 1`. A plain message is one double-quoted string with nothing after it and no backslash, `$(` or backquote: anything else stays in the comparison. The merge steps write `merged=true` and `sha=` on their pinned hand-over lines only; the merge call's success branch is pinned up to its `exit 0`, and its failure branch up to the loop's wait: only a 409 leaves — red once a call answered a 5xx or nothing —, any failure but a 4xx refusal is noted as a call that may have merged (`CALLED`), and a merge commit is tried only when GitHub refuses squash as a method. Refused anywhere in the file, comments included: a carriage return, a NEL, U+2028 or U+2029 (YAML breaks a line there, the guard's text tools do not); and, outside the four patterns of the workflow-level env and the CI workflow's name on its three lines (the project's values, which may name anything; each of those three lines is there once — `CI_NAME` set once, its comment at most once, `workflows:` by AM-6 —, since a second one would be read as neutral too): `continue-on-error`, `BASH_ENV`, `GITHUB_ENV`, `GITHUB_PATH`, an indirect expansion `${!…}`, `sudo`, a `PATH` or `HOME` assignment, a jq library file (`.jq`), a `defaults` or `shell` key however quoted or spaced, an explicit `?` key at a line's start; an empty pair of quotes inside a word; a line continuation that does not go on with an option, `&&` or `||`. Outside comment lines, wherever YAML can start a key (as AM-1 counts definitions): an explicit `?` key in a flow mapping, an alias used as a key (`*k :`, its anchor `&k defaults` set elsewhere), and a double-quoted key holding a backslash other than `\"`, `\\` or `\(` — `"\x64efaults":` is `defaults:` to YAML, not to the guard, while those three only put a quote or a backslash in a name, or are no YAML escape, so the JSON and jq keys of a script pass. In the jobs: a function other than the three the workflow defines, an `alias`, `enable`, `shopt` or `unset`, a `PUT` beyond the merge calls, and a `${{ }}` anywhere but in the value of an `if` (a step may open with it: `- if: ${{ … }}`), a `group` or an upper-case env key — never inside a block scalar such as a `run:` script, comments included, since GitHub expands it before the shell reads the script, nor in a folded `if: >-`, which takes its condition without `${{ }}`. A tab in a line of the steps is shown as such to the pins, never cut there. Checks on the text: they catch a regression and the simple ways round these pins, not every deliberate rewrite — the workflow is a held path, merged by hand, and the ruleset of § Setting it up stands against the rest. The step's behaviour ran against the local stand-in only (§ Status).
- **AM-11** — every merge waits for CI: the workflow's triggers, comments aside, are exactly `workflow_run` on `__HARNESS_CI_WORKFLOW__` and the review, `types: [completed]`, under a single `on:` key, and the file holds one merge call, `promote-from-ci`'s (the other pins are written per merging job, and a file with none would pass them). A `pull_request` trigger (the documentation fast path once had one), a manual trigger, a flow form or a second `on:` turns it red.

AM-1 also requires `CLAUDE_GATE_RE` and `PROJECT_GATE_RE` to be defined exactly once each, in the workflow-level `env`: a job- or step-level definition would shadow them. The definitions are counted on every line that is not a comment, wherever YAML can start a key — at a line's start, after `- `, or after the `{` or `,` of a flow mapping, behind an explicit `?` or node properties (`&a`, `!!str`) —, the key quoted or not, spaced or not, before its `:` or at the line's end (a key whose `:` comes on the next line). A name elsewhere in a run script is not counted (`echo "NAME: …"`, `${NAME:-…}`); a name right after a `{` or a `,`, or ending a line, reads as a key wherever it stands, run scripts included, so a message or a JSON body that lists the patterns joins them with "or" or puts them in parentheses. A script line that starts with Markdown emphasis before a colon (`*note*:`) reads as an alias key and is refused by AM-10: start it with other text. The other ways YAML builds a key — an escape, an explicit `?`, an alias — are refused by AM-10; a key built in a way the guard neither counts nor refuses is left, like any deliberate rewrite, to the hand merge of a held path.

AM-2 and AM-3 are unused: they belong to a post-merge dispatch (§ After the merge).

Now: merged by anyone else or closed, a pull request ends green after the last call as before it, and a red ending says what to check; a merge commit is made only when GitHub refuses squash as a method; a head pushed since, or a closed pull request, stops the merge green; every field of the read is a word, and a merge commit GitHub does not name turns the check red. Its guard lens found the single definition of the patterns counted on one spelling of the key, the failure branch of the merge call and the start of its loop unpinned, U+2028 and U+2029 not refused, a step opened by `- if: ${{ … }}` refused, AM-7's names counted in every step — so the dispatch of § After the merge, written the usual ways, went red —, and CI workflow names the installer accepts turning the gate red at install; and a tab, found while fixing, hid the end of a line from the steps' pins. Each is fixed, with a broken copy in the kit's tests, and the dispatch and those names stay green there. Ran against the local stand-in, not live.
- A second check of those fixes, each finding confirmed by running it against the stand-in or on rendered copies of the guard. A head pushed while a merge of this run, made by a call that answered an error, was not shown yet ended the run green and the merge unchecked: the new head check stopped before the reads that used to hand such a merge over. A head pushed during the last wait ended red as a merge to make by hand, where the same push one call earlier ended green. Definitions of the patterns were still missed when the key was an alias or an explicit `?` key in a flow mapping with its `:` on the next line, and found where none was — a message or a default in a run script —, as were escaped keys in a message, a JSON body and a jq key built by interpolation; the new start of the merge loop's pin matched a project's dispatch that retries in the same words; and the CI name was read as neutral on any line of its shape. Now a head pushed since ends green only while no call answered a 5xx or nothing, red otherwise — before a call, at a 409 and after the last call; definitions and escaped keys are counted only where YAML can start a key, with the `:` on the line or the next one; an alias used as a key and an explicit key in a flow mapping are refused, an escape that only puts a quote or a backslash in a name is not; the merge loop's pins read the merge steps only; and each line holding the CI name is there once. Each with a broken copy in the kit's tests; a dispatch retried in the merge loop's words, with messages, a JSON body and a jq key of its own, stays green there. Ran against the local stand-in, not live.
- The documentation fast path is gone (AM-11). With a ruleset that requires the CI checks, a documentation-only pull request started no CI run, so the required checks never reported and `promote-docs` was refused at every attempt; and what it merged was never scanned for secrets, since its CI was skipped and a merge made with the job token starts no `push` run. Every pull request now goes through CI, which runs on all of them and skips its costly jobs when only documentation changed; `promote-from-ci` merges them all. Unit-tested only.
