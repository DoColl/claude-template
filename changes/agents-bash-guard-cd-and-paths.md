bump: minor

- `agents`: the Bash allowlist accepts a `cd` only as `cd ./<cwd> && <command>`, written exactly so and read before quotes are removed, and no longer reads `"$CLAUDE_PROJECT_DIR"/<path>` or an absolute path under the hook's root as the project's. Claude Code sets that variable for hooks, not for the Bash tool's shell, where `"$CLAUDE_PROJECT_DIR"/x` is `/x`: `cd "$CLAUDE_PROJECT_DIR"/lib && make test ; cat os-release` ran the configured command in `/lib` and read a file there, and `cat "$CLAUDE_PROJECT_DIR"/etc/passwd` read outside the project. A bare `cd <cwd>` follows `CDPATH` first; `./` does not. In a worktree session the hook's root is the checkout the session started in, not the worktree.
- A backslash that escapes the blanks ending a segment, or ends it, is refused: the guard dropped the escaped blank while the shell kept it (`cd ./backend\ ` is `cd './backend '`).
- The verifier's brief, the convention page, the configuration seed's comment and the specification say the new forms: `cd ./<cwd> && <argv>`, `./scripts/security-checks.sh --offline`, paths relative to the root. Each form the specification now blocks was allowed before the change.

By hand: in `.claude/hooks/agent-bash-guard.config.json`, a seed, the `$comment` may still say `cd <cwd> && <argv>`: change it to `cd ./<cwd> && <argv>`. An instruction of the project that tells a sub-agent to write `"$CLAUDE_PROJECT_DIR"/…` in a Bash command writes a path relative to the root instead.
