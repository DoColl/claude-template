- `auto-merge`: before each merge call, retries included, the merge step reads the pull request, the base branch's tip and, when the tip moved, the head's merge base with it again. A pull request merged already by this workflow's token (a call that merged and answered an error) goes to the check below, and so does one the last call merged; one merged by hand meanwhile is left alone, and so is one closed meanwhile. A retargeted one, or one whose merge base moved — a commit of its head landed since the gate, so the merge would no longer write what the gate listed — is left ready and unmerged until the workflow is re-run or someone merges it by hand; one whose head was pushed since is left to the run of its new head, as a 409 would leave it — green while no call answered a 5xx or nothing; after such a call, which can merge and show it late, the run is red and says to check. A tip moved by unrelated merges does not stop it. Every field of that read is a word, `-` for one GitHub does not send: an answer without `merge_commit_sha` turns the check red instead of shifting the fields. After the last call, a pull request merged by anyone else, closed, or with a head pushed since ends the run as before a call, and one not shown merged ends it red with a message that says to check whether it is merged and what to read. Each gate holds a range that comes back without its merge base.
- `auto-merge`: a merge commit is made only when GitHub refuses squash as a method; any other failed merge call is retried with squash, after a wait and the reads above. A merge commit after a transient failure put the head's commits on the base branch and stopped the run of any pull request built on that head.
- `auto-merge`: after each merge, a new step (`Check what the merge wrote`) lists the commit GitHub created against its first parent and runs the gate's rules on it — `CLAUDE_GATE_RE` and `PROJECT_GATE_RE`, the weakened tests under `TEST_HOLD_RE` and, in `promote-docs`, anything but documentation — and turns the run red when one of them matches, or when the listing reaches 300 files or cannot be read. The gate's listing is what GitHub's merge writes only while GitHub's merge starts from the merge base its compare names, which a live test with two merge bases observed and nothing documents. The step's documentation rule is `promote-docs`' own, so a project's wider documentation set is the check's too. AM-10 pins that step, the merge call's success and failure branches (only a 409 leaves; any failure but a 4xx refusal is noted as a call that may have merged) and the merge steps' outputs, and refuses in the workflow what would make what runs differ from its text or let the check pass (a carriage return, a NEL, U+2028 or U+2029, `continue-on-error`, `BASH_ENV`, `GITHUB_ENV`, `GITHUB_PATH`, `${!…}`, `sudo`, `PATH`/`HOME` assignments, a `.jq` file, `defaults`/`shell` keys however quoted, explicit keys and alias keys, a double-quoted key holding an escape other than `\"`, `\\` or `\(` where YAML can start a key — a script's JSON and jq keys pass —, functions beyond the three the workflow defines, empty quotes inside a word, a continuation that does not go on with an option, a `PUT` beyond the merge calls, a `${{ }}` outside the value of an `if` — a step opened by `- if:` included —, a `group` or an env key or inside a block scalar); a tab in a line of the steps is shown to the pins, never cut there. AM-7 now counts three compare calls per merging job and names the tip on four lines, counts the names it follows in the gate and merge steps only and pins the hand-over of the tip and the merge base, the merge loop from its head to the call and the read after the last call, reading the merge steps only (another step, such as a dispatch after the merge, may use the same names and retry in the same words); AM-1 and AM-8 count each pattern's definitions wherever YAML can start a key — quoted, spaced, in a flow mapping, behind `?` or node properties, its `:` on the line or the next one —, not elsewhere in a run script's messages or defaults (a name right after `{` or `,`, or ending a line, counts wherever it stands), and AM-8 counts the per-file facts of both listings. The text checks read the CI workflow's name, a value of the installation like the four patterns, as a neutral word on its three lines, each held to one, the `CI_NAME` key counted in every spelling: a name the installer accepts no longer turns the gate red.
